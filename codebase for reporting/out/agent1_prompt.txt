### Trades — Overview
(chapter: Trades; type: chapter_overview)
ATS.TRADES holds executed transactions.
Key fields:
• TRADE_ID — unique trade key
• SYMBOL_ID, QUANTITY, PRICE
• BUY_CLIENT_ID / SELL_CLIENT_ID (or participants via brokers)
• TRADE_DATE, SETTLEMENT_DATE
• NOTIONAL (PRICE * QUANTITY) and possibly YIELD for bonds

Cancel and state information may live in CANCELLED_TRADES and TRADE_STATES. Negotiated trades are linked via NEGOTIATED_TRADES.

**Critical**: TRADES has NO SIDE column. There will be a time when we will have to distinguish between the types of symbols which were traded, For that We will have to go towards the SYMBOL_TYPES table. Where this information will reside and in exact these spellings, i.e SYMBOL_TYPE_ID and SYMBOL_TYPE : 1- EQUITIES,2- Bond,3- ETF . Use SELLER_BROKER_ID for sell-side, BUYER_BROKER_ID for buy-side. t.SIDE → ORA-00904. For sell-side volume/notional, filter on SELLER_BROKER_ID. For buy-side, use BUYER_BROKER_ID. Never join on both unless aggregating total activity.
Date semantics: primary_date_cols=[TRADE_DATE, SETTLEMENT_DATE] grains=[day, month, year] Pick TRADE_DATE for trading flow questions, SETTLEMENT_DATE for settlement-focused questions.

### Complete annual (or periodic) trading report for a single client – canonical pattern
(chapter: Clients; type: recipe)
When a user asks for a 'complete trading report' / 'full activity' / 'annual statement' for a specific client, always follow this exact pattern:
1. Resolve client name → CLIENT_ID via EDS_CLIENTS (case-sensitive, use = not LIKE unless wildcard).
2. Pull metrics from five sources using the same CLIENT_ID:
   • ORDERS (client places → CLIENT_ID)
   • TRADES (client can be BUYER_CLIENT_ID or SELLER_CLIENT_ID → use IN (..., ...))
   • REJECTED_ORDERS (CLIENT_ID)
   • SETTLEMENT_LEVY_DATA (CLIENT_ID + TRANSACTION_DATE)
   • REPO_CONTRACTS (BUYER_CLIENT_ID or SELLER_CLIENT_ID)
3. Use strict calendar year: >= DATE 'YYYY-01-01' AND < DATE '(YYYY+1)-01-01'
4. Never join TRADES only on BUYER_CLIENT_ID (Qwen mistake) – misses all sell-side activity → zero rows.
5. Output as category / metric / value rows (UNION ALL) for readability.
This pattern works for any year – just change the dates. Also usable for monthly/quarterly reports by adjusting the date filter.
Canonical joins (verbatim):
- ATS.TRADES.BUYER_CLIENT_ID = EDS_CLIENTS.CLIENT_ID OR ATS.TRADES.SELLER_CLIENT_ID = EDS_CLIENTS.CLIENT_ID
- ATS.REPO_CONTRACTS.BUYER_CLIENT_ID = EDS_CLIENTS.CLIENT_ID OR ATS.REPO_CONTRACTS.SELLER_CLIENT_ID = EDS_CLIENTS.CLIENT_ID
Date semantics: primary_date_cols=[ENTRY_DATETIME, TRANSACTION_DATE] grains=[year, quarter, month] Always use fixed calendar boundaries for client reporting (never rolling windows).

### Client Buy vs Sell notional and Buy/Sell ratio (TRADES)
(chapter: Trades; type: recipe)
When the user asks for client Buy/Sell notional or Buy to Sell ratio, prefer executed trades over orders.

• Source table — ATS.TRADES is the canonical fact table for executed notional (PRICE * VOLUME) keyed by BUYER_CLIENT_ID and SELLER_CLIENT_ID.
• Roles — A client can appear as buyer or seller. To aggregate cleanly per client, build a role-normalised CTE using UNION ALL:
  – First SELECT: BUYER_CLIENT_ID AS client_id, PRICE*VOLUME AS buy_notional, 0 AS sell_notional.
  – Second SELECT: SELLER_CLIENT_ID AS client_id, 0 AS buy_notional, PRICE*VOLUME AS sell_notional.
• Join pattern — Join the role-normalised CTE back to ATS.EDS_CLIENTS on client_id = CLIENT_ID. Avoid joining TRADES directly to EDS_CLIENTS on (BUYER_CLIENT_ID = CLIENT_ID OR SELLER_CLIENT_ID = CLIENT_ID); the OR condition is slow and can lead to confusing aggregations.
• Date filter — Use TRUNC(ENTRY_DATETIME,'YYYY') or a BETWEEN-style range on ENTRY_DATETIME to limit to the current year, e.g. ENTRY_DATETIME >= TRUNC(SYSDATE,'YYYY') AND ENTRY_DATETIME < ADD_MONTHS(TRUNC(SYSDATE,'YYYY'),1).
• Metrics —
  – buy_notional = SUM(buy_notional)
  – sell_notional = SUM(sell_notional)
  – buy_to_sell_ratio = buy_notional / sell_notional, with a guard for sell_notional = 0 (NULL or filter via HAVING).
• Interpretation — High Buy/Sell ratio indicates a client is net buyer in notional terms over the period; low (<1) indicates they are net seller.

Use this pattern whenever questions mention client Buy/Sell notional, Buy/Sell ratio, or similar executed activity ratios over time.
Canonical joins (verbatim):
- ATS.TRADES.BUYER_CLIENT_ID = ATS.EDS_CLIENTS.CLIENT_ID
- ATS.TRADES.SELLER_CLIENT_ID = ATS.EDS_CLIENTS.CLIENT_ID
Date semantics: primary_date_cols=[TRADES.ENTRY_DATETIME] grains=[year] Filter ENTRY_DATETIME to the relevant calendar period (e.g. current year) using range predicates rather than extracting the year from the column.

### Circular trading / wash-trade detection (round-trip patterns)
(chapter: Trades; type: recipe)
Circular trading (also called wash-trading or round-tripping) occurs when two parties repeatedly trade the same instrument back and forth.

Detection pattern (used in fs-072 and surveillance queries):
• Take all trades in a window
• For each (BuyerBroker, SellerBroker, Symbol), check if the reverse direction (SellerBroker → BuyerBroker on same Symbol) also exists
• If both directions exist → flag the pair
• Aggregate per broker (or client) to rank by number of circular relationships

Key implementation points:
• Use EXISTS subquery (or self-join) on reversed roles + same SYMBOL_ID
• Exclude self-trades (BUYER_BROKER_ID != SELLER_BROKER_ID)
• Count unique (counterparty, symbol) pairs to avoid double-counting volume
• Typical windows: last 7d, 30d, 90d, or current month

Business use:
• Market integrity monitoring
• Detecting artificial volume / liquidity inflation
• Revenue-sharing or bonus-gaming schemes between brokers

Never confuse with legitimate two-way flow – circular trading is flagged only when the reverse leg actually occurs.
Date semantics: primary_date_cols=[ENTRY_DATETIME] grains=[day, month] Use half-open rolling windows (e.g., last 30 days) or fixed calendar periods. ENTRY_DATETIME is the execution timestamp.

### Trades — canonical joins
(chapter: Trades; type: recipe)
Common joins:
• TRADES.SYMBOL_ID → SYMBOLS.SYMBOL_ID
• TRADES.CLIENT_ID / BUY_CLIENT_ID / SELL_CLIENT_ID → EDS_CLIENTS.CLIENT_ID
• TRADES.BROKER_ID / BUY_BROKER_ID / SELL_BROKER_ID → SUBSCRIBED_BROKERS.BROKER_ID
• TRADES.SETTLEMENT_TYPE_ID → SETTLEMENT_TYPES.SETTLEMENT_TYPE_ID

For bond metrics, join SYMBOL_TYPES to filter instrument universes.
Date semantics: primary_date_cols=[TRADE_DATE] grains=[day, month, year] Joins do not alter trade date semantics.

### Trades — participants and attribution
(chapter: Trades; type: section_note)
Typical joins for participant attribution:
• BUY_CLIENT_ID / SELL_CLIENT_ID → EDS_CLIENTS.CLIENT_ID
• BUY_BROKER_ID / SELL_BROKER_ID → SUBSCRIBED_BROKERS.BROKER_ID

For questions like “top clients by volume”, aggregate over both buyer and seller roles unless explicitly constrained.

**Side-specific logic**:
• Sell-side activity → use SELLER_BROKER_ID / SELL_CLIENT_ID
• Buy-side activity → use BUYER_BROKER_ID / BUY_CLIENT_ID
• Total activity (e.g. top broker) → UNION ALL or GROUP BY both sides

**Never use t.SIDE on TRADES**. For notional: SUM(PRICE * QUANTITY).
Date semantics: primary_date_cols=[TRADE_DATE] grains=[day, month, year] Attribution does not change date semantics; TRADE_DATE remains the primary key unless settlement-focused.

### Complete repo transaction cycle (leg 1 to leg 2) with all details for January 2025
Question: Give me a complete cycle of a repo market transaction from its leg 1 to leg 2 with all the information for January
SQL:
-- Complete cycle of repo market transactions (leg 1 to leg 2) with all information for January 2025
SELECT
    rc.CONTRACT_NO,
    rc.LEG,
    rc.REPO_TYPE,
    rc.ENTRY_DATETIME,
    rc.INITIAL_DATE,
    rc.TERMINATION_DATE,
    s.SYMBOL AS symbol,
    e.EXCHANGE_NAME AS exchange,
    rc.MARKET_ID,
    rc.PRICE,
    rc.VOLUME,
    rc.VALUE,
    rc.SETTLEMENT_AMOUNT,
    rc.REPURCHASE_PRICE,
    rc.REPURCHASE_SETTLEMENT_AMOUNT,
    rc.REPO_RATE,
    rc.REPO_HAIRCUT,
    rc.YIELD,
    rc.ACCRUED_PROFIT,
    rc.REPURCHASE_ACCRUED_PROFIT,
    bb.BROKER_NAME AS buyer_broker_name,
    cb.NAME AS buyer_client_name,
    ub.COMPLETE_NAME AS buyer_user_name,
    sb.BROKER_NAME AS seller_broker_name,
    cs.NAME AS seller_client_name,
    us.COMPLETE_NAME AS seller_user_name,
    st.SETTLEMENT_TYPE AS settlement_type_name,
    rc.TRADE_STATE,
    rc.IS_PROCESSED,
    rc.DIRTY_PRICE,
    rc.REPURCHASE_DIRTY_PRICE,
    rc.PAR_VALUE,
    rc.MARKET_VALUE,
    rc.ACCRUED_DAYS
FROM ATS.REPO_CONTRACTS rc
JOIN ATS.SYMBOLS s ON s.SYMBOL_ID = rc.SYMBOL_ID
JOIN ATS.EXCHANGES e ON e.EXCHANGE_ID = rc.EXCHANGE_ID
LEFT JOIN ATS.SUBSCRIBED_BROKERS bb ON bb.BROKER_ID = rc.BUYER_BROKER_ID
LEFT JOIN ATS.SUBSCRIBED_BROKERS sb ON sb.BROKER_ID = rc.SELLER_BROKER_ID
LEFT JOIN ATS.EDS_CLIENTS cb ON cb.CLIENT_ID = rc.BUYER_CLIENT_ID
LEFT JOIN ATS.EDS_CLIENTS cs ON cs.CLIENT_ID = rc.SELLER_CLIENT_ID
LEFT JOIN ATS.USERS ub ON ub.USER_ID = rc.BUYER_USER_ID
LEFT JOIN ATS.USERS us ON us.USER_ID = rc.SELLER_USER_ID
LEFT JOIN ATS.SETTLEMENT_TYPES st ON st.SETTLEMENT_TYPE_ID = rc.SETTLEMENT_TYPE_ID
WHERE rc.ENTRY_DATETIME >= DATE '2025-01-01'  -- January 2025 (current year)
  AND rc.ENTRY_DATETIME < DATE '2025-02-01'
  AND rc.LEG IN (1, 2)  -- Explicit for cycle legs
ORDER BY rc.CONTRACT_NO, rc.LEG
FETCH FIRST 200 ROWS ONLY

### Complete annual report for a single symbol (all domains – 2024 example)
Question: Give me a complete report for the symbol BCGAAAAA for the year 2024
SQL:
-- Complete symbol report – canonical pattern (2024 example)
WITH year_bounds AS (SELECT DATE '2024-01-01' AS y_start, DATE '2025-01-01' AS y_end FROM dual),
target_symbol AS (SELECT SYMBOL_ID, SYMBOL FROM ATS.SYMBOLS WHERE SYMBOL = 'BCGAAAAA'),
daily AS (SELECT SUM(si.TURNOVER_VALUE) AS turnover, SUM(si.TRADES_COUNT) AS trades_cnt, AVG(si.CLOSE_PRICE) AS close_price, MAX(si.HIGH_PRICE) AS high, MIN(si.LOW_PRICE) AS low FROM ATS.SYMBOL_DAILY_INDICATORS si JOIN target_symbol ts ON si.SYMBOL_ID = ts.SYMBOL_ID CROSS JOIN year_bounds yb WHERE si.STATS_DATE >= yb.y_start AND si.STATS_DATE < yb.y_end GROUP BY si.SYMBOL_ID),
intraday AS (SELECT SUM(s.VOLUME) AS volume, SUM(s.VALUE) AS turnover FROM ATS.SYMBOL_INDICATORS s JOIN target_symbol ts ON s.SYMBOL_ID = ts.SYMBOL_ID CROSS JOIN year_bounds yb WHERE s.ENTRY_DATETIME >= yb.y_start AND s.ENTRY_DATETIME < yb.y_end GROUP BY s.SYMBOL_ID),
orders AS (SELECT COUNT(*) AS cnt, SUM(o.VOLUME) AS vol, SUM(o.VOLUME*o.PRICE) AS notional, SUM(CASE WHEN o.SIDE='B' THEN o.VOLUME ELSE 0 END) AS buy_vol, SUM(CASE WHEN o.SIDE='S' THEN o.VOLUME ELSE 0 END) AS sell_vol, AVG(o.PRICE) AS avg_price FROM ATS.ORDERS o JOIN target_symbol ts ON o.SYMBOL_ID = ts.SYMBOL_ID CROSS JOIN year_bounds yb WHERE o.ENTRY_DATETIME >= yb.y_start AND o.ENTRY_DATETIME < yb.y_end GROUP BY o.SYMBOL_ID),
trades AS (SELECT COUNT(*) AS cnt, SUM(t.VOLUME) AS vol, SUM(t.PRICE*t.VOLUME) AS notional, AVG(t.PRICE) AS avg_price FROM ATS.TRADES t JOIN target_symbol ts ON t.SYMBOL_ID = ts.SYMBOL_ID CROSS JOIN year_bounds yb WHERE t.ENTRY_DATETIME >= yb.y_start AND t.ENTRY_DATETIME < yb.y_end GROUP BY t.SYMBOL_ID),
rejected AS (SELECT COUNT(*) AS cnt FROM ATS.REJECTED_ORDERS ro JOIN target_symbol ts ON ro.SYMBOL_ID = ts.SYMBOL_ID CROSS JOIN year_bounds yb WHERE ro.ENTRY_DATETIME >= yb.y_start AND ro.ENTRY_DATETIME < yb.y_end GROUP BY ro.SYMBOL_ID),
repo AS (SELECT COUNT(*) AS legs, SUM(rc.SETTLEMENT_AMOUNT) AS cash_flow, AVG(rc.REPO_RATE) AS rate, AVG(rc.REPO_HAIRCUT) AS haircut FROM ATS.REPO_CONTRACTS rc JOIN target_symbol ts ON rc.SYMBOL_ID = ts.SYMBOL_ID CROSS JOIN year_bounds yb WHERE rc.ENTRY_DATETIME >= yb.y_start AND rc.ENTRY_DATETIME < yb.y_end GROUP BY rc.SYMBOL_ID)
SELECT ts.SYMBOL,
  NVL(d.turnover,0) AS daily_turnover, NVL(d.trades_cnt,0) AS daily_trades_count, NVL(d.close_price,0) AS avg_daily_close,
  NVL(i.volume,0) AS intraday_volume, NVL(i.turnover,0) AS intraday_turnover,
  NVL(o.cnt,0) AS orders_count, NVL(o.vol,0) AS order_volume, NVL(o.notional,0) AS order_notional, NVL(o.buy_vol,0) AS buy_volume, NVL(o.sell_vol,0) AS sell_volume,
  NVL(t.cnt,0) AS trades_count, NVL(t.vol,0) AS trade_volume, NVL(t.notional,0) AS trade_notional,
  NVL(r.cnt,0) AS rejected_orders_count,
  NVL(p.legs,0) AS repo_legs, NVL(p.cash_flow,0) AS repo_cash_flow, NVL(p.rate,0) AS avg_repo_rate
FROM target_symbol ts
LEFT JOIN daily d ON d.SYMBOL_ID = ts.SYMBOL_ID
LEFT JOIN intraday i ON i.SYMBOL_ID = ts.SYMBOL_ID
LEFT JOIN orders o ON o.SYMBOL_ID = ts.SYMBOL_ID
LEFT JOIN trades t ON t.SYMBOL_ID = ts.SYMBOL_ID
LEFT JOIN rejected r ON r.SYMBOL_ID = ts.SYMBOL_ID
LEFT JOIN repo p ON p.SYMBOL_ID = ts.SYMBOL_ID
FETCH FIRST 200 ROWS ONLY;

### Clients with >5 orders last month but fewer executions
Question: List clients who placed more than 5 orders in last month but had lesser executions with their count
SQL:
WITH date_range AS (
  SELECT ADD_MONTHS(TRUNC(SYSDATE, 'MM'), -1) AS start_date,
         TRUNC(SYSDATE, 'MM') AS end_date
  FROM dual
),
client_orders AS (
  SELECT o.CLIENT_ID, COUNT(*) AS total_orders
  FROM ATS.ORDERS o
  CROSS JOIN date_range dr
  WHERE o.ENTRY_DATETIME >= dr.start_date
    AND o.ENTRY_DATETIME < dr.end_date
  GROUP BY o.CLIENT_ID
  HAVING COUNT(*) > 5
),
client_executions AS (
  -- count executions for both roles in TRADES
  SELECT client_id, COUNT(*) AS total_executions
  FROM (
    SELECT t.BUYER_CLIENT_ID AS client_id
    FROM ATS.TRADES t
    CROSS JOIN date_range dr
    WHERE t.ENTRY_DATETIME >= dr.start_date
      AND t.ENTRY_DATETIME < dr.end_date
    UNION ALL
    SELECT t.SELLER_CLIENT_ID AS client_id
    FROM ATS.TRADES t
    CROSS JOIN date_range dr
    WHERE t.ENTRY_DATETIME >= dr.start_date
      AND t.ENTRY_DATETIME < dr.end_date
  ) x
  GROUP BY client_id
)
SELECT
  ec.NAME AS client_name,
  co.total_orders,
  NVL(ce.total_executions, 0) AS total_executions
FROM client_orders co
LEFT JOIN client_executions ce ON ce.client_id = co.CLIENT_ID
JOIN ATS.EDS_CLIENTS ec ON ec.CLIENT_ID = co.CLIENT_ID
WHERE NVL(ce.total_executions, 0) < co.total_orders
ORDER BY co.total_orders DESC
FETCH FIRST 200 ROWS ONLY;
